# Следующий этап: реальный LinkedIn

## Проверять до реализации

1. С разрешённой сессией пользователя зафиксировать текущий сетевой запрос поиска **Posts**,
   сортировку по свежести и временное окно. Не использовать поиск обычных Jobs.
2. Проверить ответ на содержимое постов, а не только HTTP 200: старые Voyager search-обёртки
   могут возвращать пустые карточки.
3. Отдельно проверить ленту публикаций известного автора.
4. На известных постах измерить задержку и пропуски. Только после этого выбирать рабочий путь.

## Контракт адаптера

`fetchPosts(): Promise<Post[]>` возвращает нормализованные данные. `id` должен быть
стабильным activity/ugcPost URN или идентификатором исходной публикации, не случайным UUID.
`publishedAt` — фактическое время LinkedIn; `firstSeenAt` — локальное время обнаружения.
Время получения ответа не подменяет время публикации.

Первый адаптер использует прямые HTTP-запросы. Playwright и управление DOM в проект не добавлены.
Браузер может понадобиться для ручной авторизации и исследования текущих запросов.

## Поведение при ошибках

- Timeout на каждый HTTP-запрос; ограниченные страницы и параллелизм.
- 401/403, checkpoint и CAPTCHA — явная ошибка доступа, без попыток обхода.
- 429 — пауза с учётом Retry-After; не повышать параллелизм.
- Неизвестный формат ответа — ошибка контракта, не «найдено ноль постов».
- Cookies хранятся локально вне Git. Не просить присылать cookies в чат.
- Ограничить размер ответа и число результатов. Пагинация и overlapping window должны иметь checkpoint.

Сейчас интерфейс возвращает пакет целиком: большие объёмы потребуют AsyncIterable/постраничного
контракта и сохранения checkpoint после постановки страницы в очередь. Не заявлять,
что существующий mock уже подтверждает масштабируемость реального сбора.
