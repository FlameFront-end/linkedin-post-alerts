# Защита от избыточных запросов к LinkedIn

## Что включено

Все запросы collector к LinkedIn — лента, поиск, описания, подгрузки и Jobs — проходят через общий ограничитель. Он хранится в PostgreSQL (`processing.source_state`, ключ `traffic_protection`). Счётчики и остановки не сбрасываются перезапуском контейнера или диагностической команды.

Текущие собственные ограничения сервиса:

- Между запросами — не менее 20 секунд. Одновременно выполняется один запрос, включая разные процессы collector.
- Общий предел — 20 запросов за скользящий час и 150 за скользящие 24 часа.
- Внутри общего бюджета поиск имеет отдельный предел: 4 запроса в час и 20 в сутки.
- Минимальные интервалы циклов: лента 10 минут, поиск 30 минут, Jobs 60 минут. Более частые старые настройки не обходят эти минимумы.
- На старте цикл ленты/поиска ограничен одним запросом, Jobs — двумя (список и одно описание). После успешных запросов бюджет растёт постепенно, максимум до 3/2/4 запросов за цикл соответственно.

**Это наши ограничения нагрузки, а не опубликованные LinkedIn безопасные пороги.** LinkedIn может ограничить автоматизированный доступ и при меньшей частоте. Защитный режим уменьшает скорость и глубину сбора; когда дневной бюджет исчерпан, новые запросы ждут освобождения скользящего окна. Полное покрытие и доставку за несколько минут в этом режиме не обещаем.

## Реакция на проблемы

- Сообщение о необычном поисковом трафике → `search_restricted`. Весь поиск по любым ключевым словам остаётся выключенным до ручного подтверждения. Нет попыток другого поискового запроса для обхода ограничения. После обнаружения дополнительно действует наша общая пауза не менее часа.
- Реальная проверка доступа/входа → сохраняем общую остановку всех источников.
- HTTP 429 → общая пауза минимум на час, затем 2/4/8… часов при повторении. Более длинный Retry-After соблюдается; срок больше недели требует ручной проверки.
- Сеть/временные HTTP-ошибки → 5/10/20/40… минут ожидания, максимум 6 часов. Ошибочный источник не продолжает перебирать остальные цели во время паузы.
- Непонятный формат страницы → источник останавливается для проверки структуры ответа. Нельзя считать экран ограничения пустой успешной выдачей.
- Отдельная удалённая карточка (404/410) → обычный пропуск с отложенной попыткой; это не блокировка всего аккаунта.
- Локальный лимит запросов → ожидаем окно без аварийных уведомлений о «неработающем LinkedIn».

Запрос резервируется в транзакции перед обращением к LinkedIn. Между процессами действует общая аренда; аварийно оборванная аренда истекает, но уже потраченный бюджет остаётся. Если база или состояние защиты недоступны/повреждены, запрос не отправляется.

## Проверки и восстановление

`npm run linkedin:check` теперь **не обращается к LinkedIn**. Показывает сохранённое состояние, лимиты и причины остановки. `/status` collector дополнительно показывает интервалы источников.

Явная одиночная диагностика:

```sh
npm run linkedin:check -- --probe feed
```

Она подчиняется общим лимитам и не может пройти через сохранённую остановку.

После того как владелец подтвердил, что обычный поиск в браузере снова работает:

```sh
npm run linkedin:check -- --confirmed-probe search
```

Команда не сбрасывает дневной/часовой бюджет или обязательную паузу. Она разрешает ровно один проверочный запрос. После успеха до следующего запроса поиска выдерживается 30 минут. Если процесс оборвался во время проверки, автоматического повторного запроса не будет: требуется новое подтверждение.

Для общей проблемы входа существует отдельное явное подтверждение аккаунта:

```sh
npm run linkedin:check -- --confirmed-account-probe feed
```

Команды не снимают `COLLECTION_PAUSED=true`. Полное возобновление сбора выполняется отдельно после успешной проверки. Пока LinkedIn показывает приостановку поиска, проверочные запросы не запускаем.

## Проверено

Локальные тесты проверяют сохранение ограничения после перезапуска, общую квоту Jobs/ленты/поиска, суточный бюджет, меньший бюджет поиска, Retry-After, возрастающие паузы, один проверочный запрос, оборванную проверку, недоступную карточку и отсутствие ложного срабатывания на текст вакансии.

В интеграционной проверке два независимых ограничителя одновременно пытаются потратить последний доступный запрос через настоящую PostgreSQL: разрешение получает один. При текущем ограничении аккаунта живые нагрузочные прогоны не выполнялись.

Дополнительно: создание LinkedInClient с обычным живым транспортом без защиты запрещено проверкой конфигурации. Правила для будущих изменений и диагностики записаны в AGENTS.md, чтобы разовая проверка из терминала не обходила общий бюджет.

Итоговая проверка этой версии: 122 unit-теста и 2 интеграционных сценария проходят. После перезапуска настоящего контейнера сохранены search_restricted и COLLECTION_PAUSED=true; счётчик запросов равен нулю. Живой поиск для проверки защиты не запускался.
